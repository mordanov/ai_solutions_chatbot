# Implementation Plan: Admin Reservation Approval

**Branch**: `002-admin-approval` | **Date**: 2026-08-11 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `specs/002-admin-approval/spec.md`

## Summary

Stage 3 of the Intelligent Parking Reservation Chatbot adds human-in-the-loop approval for reservations. When all reservation fields pass validation, the chatbot dispatches an SMTP email to the administrator containing full reservation details and bearer-token-secured approve/reject API endpoints. A new `chatbot.approval` module manages pending request state in an in-process dictionary keyed by session ID. On each subsequent user message, a new LangGraph node checks whether a pending approval decision has arrived and delivers the outcome before processing the new query. Two new admin API endpoints record approval and rejection decisions.

## Workflow Design

### LangGraph Node Map (updated)

```
START
  └─► pending_check_node
        ├─[decision arrived]──────────────────► guard_rails_node ─► respond ─► END
        └─[no pending / clear]─► route_intent
                                    ├─► retrieve_and_generate ─► guard_rails_node ─► respond ─► END
                                    ├─► dynamic_data_node     ─► guard_rails_node ─► respond ─► END
                                    ├─► out_of_scope_node     ─► guard_rails_node ─► respond ─► END
                                    └─► reservation_collector_node
                                              └─► reservation_validator_node
                                                    ├─[fields missing]──────────────► respond ─► END
                                                    └─[all valid / submitted]
                                                              └─► approval_request_node
                                                                        └─► guard_rails_node ─► respond ─► END
```

### Reservation Status Lifecycle

```
draft  ──(all fields valid)──► submitted  ──(email sent)──► pending_approval
                                                                 ├──(admin approves)──► approved   (terminal)
                                                                 ├──(admin rejects)───► rejected   (terminal)
                                                                 └──(timeout)─────────► expired    (terminal)
```

`submitted` is transient: `reservation_validator_node` sets it, then `approval_request_node` immediately transitions to `pending_approval` after dispatching the email.

### pending_check_node Logic

```
pending_check_node(state):
  lookup = pending_store.get_pending_for_session(state.session_id)
  if lookup is None:
    return state  # route to route_intent
  if lookup.is_expired():
    pending_store.expire(lookup.request_id)
    state.reservation.status = "expired"
    state.response_draft = "Your reservation request timed out. Please resubmit."
    return state  # route to guard_rails_node
  if lookup.decision is not None:
    if lookup.decision == "approved":
      state.reservation.status = "approved"
      state.response_draft = f"✅ Your reservation was approved!\n..."
    else:
      state.reservation.status = "rejected"
      state.response_draft = f"❌ Your reservation was not approved.\nReason: {lookup.reason}"
    pending_store.clear(state.session_id)
    return state  # route to guard_rails_node
  # still pending — continue normal flow
  return state  # route to route_intent
```

### Guard-Rails PII Bypass (updated)

The bypass in `guard_rails_node` is extended: skip PII scan when `state.reservation.status in {"pending_approval", "approved", "rejected", "expired"}`. These messages legitimately echo the user's own reservation data back to them.

### Email Format

The SMTP email sent to the admin contains:
- Subject: `[Parking Reservation] New request from {first_name} {surname} — {request_id}`
- Body: full reservation details + two curl commands to approve or reject via the API bearer token
